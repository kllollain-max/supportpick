원고 작성과 실제 큐 저장
1. 가장 최근 완료된 main의 supportpick-operations.yml 실행과 supportpick-runtime-state artifact를 읽는다. 전체 실행 conclusion만으로 수집 실패라고 단정하지 말고 manifest 해시와 load_feed/read_current/verify_snapshot으로 실제 세대·완전성·수집 신선도를 확인한다. sourceOnly나 수집 성공 시각을 현재 접수 검증으로 바꾸지 않는다. 다운로드가 필요하면 GitHub artifact 도구의 반환 파일을 이용하고 자격정보를 출력하지 않는다.
2. 실제 게시 원장 최근 20건과 현재 큐를 읽는다. tools/supportpick_threads.py writer-input 또는 동일 검증된 읽기 경로로 다음 24시간의 미예약 정규 슬롯 최대4개를 준비한다. 이미 작성한 READY 원고가 사실·상태·미디어·유효기간 검사에 통과하면 재사용한다. 예약된 pending의 본문·해시·이미지·형식은 절대 교체하지 않는다.
3. 마스터 프롬프트 전체를 실제 작성 입력으로 사용한다. 공식 기관의 현재 공고·신청 페이지·정정/종료 안내를 대조하고, 검증 가능한 후보 중 같은 서비스 ID의 보조금24 원본 serviceList.조회수 내림차순을 유지한다. 동률은 마감 가까운 순·ID 순이다. 누락 조회수는 추정하지 않는다. 조회수는 누적 지표이며 실시간 검색량·신청자 수라고 표현하지 않는다. 선택한 후보보다 조회수가 높은 후보가 HOLD/SKIP이면 queue.selection_notes에 사업 ID·판단·구체 이유·확인한 출처를 모두 기록한다. 다른 큐에 이미 예약한 사업을 다시 예약하지 않는다.
4. 같은 KST 날짜에 P1~P9 중 사실에 적합한 서로 다른 패턴4개를 사용한다. 기본 조합 P1 생활 상황, P5 자격 체크, P6 준비 절차, P8 작은 정보 목록을 참고하되 사업에 맞게 교체하고 다음날에도 도입/전개 반복을 줄인다. P2 오해 정정이나 P7 변화/마감은 실제 근거가 있을 때만 사용한다. 형식명만 바꾸지 말고 첫 문장·전개 순서도 비교한다.
5. 새 원고는 supportpick.writer.v1 JSON의 단독 본문1개와 reply_texts:[]이다. 과거의 본문+답글2개 정책은 새 원고에 적용하지 않는다. 250~450자를 편집 출발점으로 하고 실제 상한500자(공백·개행·CTA 포함)를 계산한다. 마지막 줄은 정확히 '자세한 사항은 프로필링크 확인'을 1회 넣는다. 본문·답글 URL, 도메인, 단축주소, 우회주소, 기본 해시태그를 넣지 않는다. 추가 댓글·저장·공유 유도를 붙이지 않는다. 출처 URL은 내부 검수에만 보존한다. 실제 없는 기능·금액·후기·긴급성·확정 지급을 만들지 않는다.
6. READY만 게시 후보로 저장한다. DRAFT/HOLD/SKIP을 READY로 바꾸기 위해 근거를 꾸미지 않는다. 공식자료가 부족하면 다른 검증 가능한 후보로 진행한다. 필수 조건·지급 단위·최대액·대출 상환·자부담·지역·시기를 명확히 한다. review에 실제 열람방법, 확인시각, 선택사업ID와 출처, 지원되는 주장, 미확인 항목, 검수결과를 남긴다. source_fingerprint는 검증기 함수로 계산한다. 마스터 해시, source_generation, prepared_at, expires_at(최대24시간), 정확한 slot을 queue wrapper에 넣는다. API 수집시각과 실제 원문 검수시각을 구분한다.
7. 이미지 교대는 성공 원장과 실제 예약을 기준으로 기존 순서를 이어간다. IMAGE는 social/assets.json의 혜택별 승인 이미지 또는 검수된 _rotation 2종을 사용한다. main/social/images의 허용된 URL만 쓴다. social/image-review.json의 시각검수와 현재 파일 SHA를 재대조하고 일치한 현재 시각을 UPSTREAM_VERIFIED로 기록한다. 이때 새 시각검수를 하지 않았다면 '오늘 직접 봤다'고 쓰지 않는다. 24시간 지난 evidence를 날짜만 바꿔 복사하지 말고 실제 재대조를 수행한다. 금액·대상·기간·한정어가 이미지에 있으면 본문과 일치해야 한다. asset_sha256·실제내용 alt_text·이미지 URL evidence를 기록한다. 이미지가 없거나 불일치하면 보류하고 TEXT로 바꾸지 않는다.
8. 앞 회차가 전송 전에 실패/건너뛰어지면 아직 미예약인 미래 슬롯의 후보 우선순위와 IMAGE/TEXT 예상 순서를 다시 계산한다. 만료된 미게시 슬롯은 다시 발행하지 않으며 원고와 이유를 점검 기록에 남겨 보관하고 현재 큐에서 제거하거나 HOLD로 바꾼다. 미전송 같은 사업을 다른 미래 슬롯으로 옮길 때 두 READY가 남지 않도록 한다. 이미 보낸 글과 pending은 그대로 유지한다.
9. validate_ready_entry 및 preview로 큐 전부를 검증하고, 허용된 미래시각 시뮬레이션이면 실제 발송시 최신자료 재검증 필요를 표시한다. 현재 source가 다음날 발송까지 신선하다고 가정하지 않는다. 조건부 저장 후 다시 읽어 동일 내용·해시를 확인한다. 문서만 저장하고 원고 큐를 비워 둔 채 '자동 작성 반영'이라고 보고하지 않는다. 실제 발송은 기존 Actions 게시기가 검수 큐를 소비한다.

장애 점검과 자동 복구
10. .github/workflows/supportpick-threads.yml 및 필수 supportpick-operations.yml의 최신 실제 실행·job 로그·artifact·코드 SHA를 읽는다. observed_run_versions의 run_id/run_attempt/status/conclusion/updated_at/head_sha를 함께 비교한다. 같은 run ID도 attempt나 종료상태가 바뀌면 새 점검으로 처리한다. 마지막 체크포인트까지 페이지 이동하고 조건부로 관측 버전을 보존한다. 정상 후보 없음/중복 제외와 실제 실패를 구분한다.
11. 실패 지문, 확인된 원인과 가설, 마지막 성공, stage, container/게시 ID, 본문·자산 해시, 재시도 예산, 다음 재개 조건을 기록한다. 실패 로그만으로 '게시 없음'을 단정하지 말고 원장·실제 영수증·원격 이력을 먼저 확인한다. 완료된 장애나 과거 성공을 새 결과로 반복하지 않는다. 초기 41796747628은 PR7과 복구실행41797892734로 해결된 사건이므로 현재 원장을 확인한 뒤 해결상태를 유지한다.
12. GET 일시 오류만 구현된 최대3회·2/5초·Retry-After 규칙으로 재시도한다. 인증/권한400·401·403, 잘못된 계정, API 의미 오류는 무한 재시도하지 않는다. POST/컨테이너 생성/발행은 결과 불명확 시 반복하지 않는다. pending sending에 영수증이 없으면 지우거나 다음 단계로 넘기지 않는다. 실제 원격 근거가 있을 때만 조건부 복구한다.
13. 확인된 코드 원인은 기존 열린 PR을 재사용하거나 새 branch/PR로 최소 수정하고, 동일 장애를 재현하는 회귀 검사·관련 CI·실제 읽기 경로를 검증한다. 사용자 승인 범위인 Threads·필수 수집 수정만 main에 병합·적용한다. 계정guard·하루한도·main/첫attempt·CAS·pending차단·공식 사실·신선도·이미지교대 검사를 약화하지 않는다. 사이트 공개 배포나 운영 정책 확대는 하지 않는다.
14. 예약 전 실패가 확인되고 원래 정규슬롯의 2시간 허용창이 남으면 새 workflow_dispatch의 mode=resume-unreserved-slot과 원래 recovery_cron으로만 재개한다. 기존 슬롯이 원장에 있으면 다시 만들지 않는다. 이미 본문 ID가 있는 pending은 mode=resume-pending과 정확한 resume_main_id를 사용해 원래 본문을 검증하고 미완료 단계만 마친다. 새 단독 본문도 기존3부분 pending도 실제 record schema에 따라 처리한다. 이미 지난 슬롯 소급발행, 실패 workflow rerun(두번째attempt), 임의 현재분 publish-one-now, 테스트 새게시, 한도증액은 하지 않는다.
15. workflow_dispatch 도구가 없으면 허용된 GitHub UI 경로를 사용한다. 접근/권한/로그인/토큰 등 실제 차단이 있으면 성공으로 꾸미지 말고 준비된 코드·검수원고·남은 조치를 구분한다. 키·토큰을 대화에 요구하거나 출력하지 않는다. 자격정보 교체가 필요하면 정확한 소유자 조치만 보고하고 우회·새권한·유료도입을 하지 않는다.

기록과 보고
