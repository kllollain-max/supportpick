# 지원금픽 Threads 원고 작성과 자동 복구

2026년 11월 6일 사용자가 제공한 지원금픽 스레드 작성 프롬프트와 추가 운영 지시를 적용한다. 대상은 `kllollain-max/supportpick`, Threads `@hid_1004`다.

## 작성 원문과 게시 경로

`social/supportpick-writer-master-prompt.txt`는 첨부 DOCX의 B 마스터 프롬프트 원문이다. SHA-256은 `07db46fe40e3c392efe6810dc4909549643d6d615b2232270860ba5dec30a918`이다. 원본 DOCX의 SHA-256은 `a964d4afc757cf0501af5858ab984e78d851f68ea6b54233bc5bc1b9fe533f32`다.

ChatGPT의 기존 시간별 작성·복구 작업이 이 원문 전체와 최신 공식 자료·게시 이력을 읽어 `supportpick.writer.v1` 원고를 만든다. GitHub Actions가 LLM에 직접 접속하는 구조가 아니다. 게시기는 `supportpick-threads-state` 브랜치의 `social/threads-writer-queue.json`에 있는 검수 원고를 받아 사실 원문의 해시·시각·계정·회차·형식·미디어·분량·CTA를 확인한 뒤 예약한다. 검수 없는 기존 정형 문안으로 대체하지 않는다.

새 원고는 단독 본문 한 개와 `reply_texts: []`를 사용한다. 마지막 줄은 정확히 `자세한 사항은 프로필링크 확인`이다. 게시 문안에는 링크·주소 우회 표기·기본 해시태그를 넣지 않는다. 공식 URL과 검수 근거는 내부 원장에 보존한다. 기존 세 부분 게시물과 pending은 원문·해시·영수증을 유지하여 복구한다.

## 일정과 형식

기존 한국시간 08시·12시·16시·20시 일정, 회차별 2시간 지연 허용, 하루 최대 본문 4건을 유지한다. GitHub 예약 실행의 실제 시작은 지연될 수 있다. 지난 회차를 소급 발행하거나 검사용 게시물을 만들지 않는다.

동일 KST 날짜에는 P1부터 P9까지 중 사실에 적합한 서로 다른 패턴 네 개를 사용한다. 기본 후보 조합은 생활 상황 P1, 자격 체크 P5, 준비 절차 P6, 작은 정보 목록 P8이며 사업에 맞게 대체한다. 도입 문장·전개도 검수한다. 형식 이름만 바꾼 반복 문안이나 근거 없는 오해·마감·변화를 만들지 않는다.

검증 가능한 후보 중 보조금24 원본 누적 조회수 순서를 우선한다. 상위 후보를 보류하면 사실 충돌·접수 상태 미확인·종료 등 실제 이유를 기록한다. 조회수를 실시간 검색량이나 신청자 수로 설명하지 않는다. 수집 성공 시각만으로 현재 접수를 확정하지 않는다.

## 이미지

원장에 기록된 기존 순서를 이어 TEXT와 IMAGE를 교대한다. 실패 전에 예약하지 않은 회차는 교대 순서를 소비하지 않는다. pending은 전체 다음 게시를 차단하고 복구 시 원래 이미지·본문을 유지한다. 앞 회차가 건너뛰어졌다면 미예약된 미래 원고의 예상 미디어를 다시 계산하고 검수한다.

검수된 두 공통 이미지는 1254×1254 정사각형이며 기록은 `social/image-review.json`에 있다. 이미지 회차에는 승인 URL과 체크아웃 파일 SHA-256이 일치해야 한다. 이미지가 없거나 불일치하면 보류하며 텍스트로 전환하지 않는다. 사업별 승인 이미지가 있으면 기존 선택 정책에 따라 우선할 수 있다. 공통 브랜드 이미지에는 금액·대상·기간이 없으므로 그러한 정보가 그림에 있다고 쓰지 않는다.

## 원고 큐 계약

루트 필드는 `schema_version: supportpick.queue.v1`, `brand: supportpick`, `username: hid_1004`, `prompt_sha256`, `entries`다. 각 entry에는 정확한 `slot`, `benefit_id`, `source_fingerprint`, `source_generation`, `prepared_at`, `expires_at`, `writer`가 있다. IMAGE는 `asset_sha256`도 필수다.

원고는 준비 후 최대 24시간만 유효하다. 본문 상태 READY, 모든 필수 검수 PASS, 500자 이내 실제 계산, 정확한 CTA, 같은 날 형식 중복 없음, 근거 확인 시각, 최신 자료와 사실 해시 일치가 필요하다. DRAFT·HOLD·SKIP을 게시하지 않는다. 코드 검사는 공식 사실을 스스로 증명하지 않는다. 실제 작성 작업이 공식 원문을 확인하고 증거와 확인 범위를 정확히 남겨야 한다.

큐 쓰기는 매번 최신 blob SHA를 읽은 뒤 조건부로 수행한다. 다른 작업의 변경을 덮어쓰거나 게시 원장을 초기화하지 않는다. 이미 예약한 원고는 변경하지 않는다. 아직 예약하지 않은 미래 원고의 사실·상태·이미지 순서가 바뀌면 이전 원고와 변경 이유를 점검 기록에 남기고 재검수한 교체본만 저장한다.

`python tools/supportpick_threads.py writer-input`은 최신 검증 수집본과 실제 원장으로 작성 입력을 만든다. `preview`는 게시 없이 원고를 검증한다. 로컬 점검에서는 `--state`, `--ledger`, `--queue`를 사용할 수 있으며 실제 publish는 원격 상태만 사용한다. 미래 시각 preview는 해당 회차를 시뮬레이션하며, 실제 전송 시 최신 수집본·원장을 다시 확인해야 한다.

## 자동 복구

기존 시간별 자동화 `6aeaefe5fd708191a3e8a67b3667fb8f`가 새 원고 준비와 장애 점검을 맡는다. 실패 run ID뿐 아니라 attempt·status·conclusion·updated_at·head_sha의 변화를 기록한다. 같은 실패를 반복 보고하거나 무한 재시도하지 않는다.

읽기 전용 GET의 일시 통신 오류와 HTTP 408·429·500·502·503·504는 총 3회 이내에 재시도한다. 기본 간격은 2초와 5초이며 서버 Retry-After를 존중한다. 30초를 넘거나 잘못된 Retry-After는 기다리는 척 통과시키지 않고 보류한다. 인증·권한·형식 오류는 반복하지 않는다. 계정 오류는 HTTP 상태와 안전한 숫자 오류 코드만 기록하고 토큰·응답 원문은 출력하지 않는다.

POST는 자동 반복하지 않는다. 영수증이 불명확하면 원격 게시 이력을 조회해 중복을 방지한다. 원장 예약 전 실패가 확인되고 같은 회차의 2시간 창이 남아 있으면 새 첫 실행의 `resume-unreserved-slot`과 원래 `recovery_cron`으로 복구한다. 이 경로도 원래 회차 키·하루 한도·검수 큐·계정·main·중복 검사를 그대로 통과해야 한다. 예약된 본문 ID가 있으면 `resume-pending`으로 그 ID만 복구한다. sending 상태에 영수증이 없으면 임의로 지우지 않는다.

확인된 코드 원인은 해당 오류를 재현하는 회귀 검사와 CI를 통과시킨 뒤 승인된 Threads 범위에서 적용한다. 토큰 만료·권한 거부처럼 소유자 조치가 필요한 문제는 정확한 차단과 필요한 조치만 보고한다. 보안 제한을 우회하거나 새 권한·유료 서비스를 추가하지 않는다. 준비 완료, 코드 적용, 자연 예약 회차의 실제 게시 성공을 구분한다.

### 계정 오류를 구분하는 수동 읽기 진단

`SupportPick Threads Account Diagnostic` 워크플로는 기존 토큰과 계정 ID만 사용하여 공식 API의 접속 주소·인증 전달 방식 차이와 자기 토큰 상태를 읽기 전용으로 구분한다. 일반 게시 실패를 무작정 재실행하기 전에 새 진단이 필요한 근거가 있을 때 사용한다. 원래 경로가 성공하면 불필요한 대안 조회를 생략하고, 전체 조회는 최대 5회로 제한한다. 다른 계정 확인·속도 제한·일시 장애에서는 비교를 중단한다.

이 워크플로는 저장소 읽기 권한만 가지며 게시·원장 예약·토큰 교체를 하지 않는다. 응답 원문, 토큰, 사용자 ID, 이름, URL 및 예외 문자열을 출력하지 않고 허용된 상태·숫자 오류 코드·계정 일치 여부·필수 권한 유무만 보존한다. 리디렉션을 자동 추적하지 않는다.

워크플로의 성공은 **진단 수집 완료**이며 계정 정상 또는 게시 성공을 뜻하지 않는다. 결과 파일 `threads-account-diagnostic.json`의 개별 판정을 확인한다. 대안 경로가 성공해도 운영 요청을 자동 교체하지 않으며, 확인된 차이만 별도 수정·검증한다. 권한·유효성 정보가 없으면 `unknown`을 유지한다. 동일한 진단 결과를 반복 실행하거나 소유자의 승인·자격정보를 대신 변경하지 않는다.
